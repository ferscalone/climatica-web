# Climatica Web — как это устроено

Документ для разработчика: из каких частей состоит система, как по ней идут данные,
где лежат важные места и что стоит знать перед доработками.

## 1. Общая схема

```
 Камеры (Modbus RTU over UDP :5001)
        │  запрос раз в POLL_INTERVAL_MS
        ▼
 ┌──────────────────────── backend (FastAPI) ─────────────────────────┐
 │ ChamberPoller ×N ──► measurements (БД)                             │
 │   │  проверка порогов (кэш ThresholdService)                        │
 │   │  детектор переходов online/offline, норма/вне нормы             │
 │   ├──► broadcaster ──► WebSocket /ws ──► браузеры ("measurement")   │
 │   └──► alert_service.publish(...)                                  │
 │                                                                    │
 │ PUT /api/thresholds ──► thresholds + audit_log ──► publish(...)     │
 │                                                                    │
 │ AlertService (пул уведомлений, asyncio.Queue)                       │
 │   1. alert_events (БД) + logs/journal.log                          │
 │   2. WebSocket → все вкладки ("alert")                              │
 │   3. каналы доставки → TelegramBotChannel ──HTTP──┐                 │
 │   retry-цикл: недоставленные раз в ALERT_RETRY_INTERVAL             │
 └───────────────────────────────────────────────────┼────────────────┘
                                                     ▼
                              ┌─────── telegram-bot (aiohttp + PTB) ──────┐
                              │ POST /internal/send → TELEGRAM_CHAT_IDS    │
                              │ polling api.telegram.org: /status,         │
                              │ /thresholds ──HTTP──► backend /api/...     │
                              └────────────────────────────────────────────┘
```

Три контейнера: `db` (PostgreSQL), `backend`, `telegram-bot`. Бот и backend
общаются только по HTTP внутри compose-сети; наружу публикуется только порт 8000.

## 2. Backend по модулям

### `app/modbus/` — протокол
- `crc.py` — CRC16 Modbus, перенесён из оригинала без изменений.
- `client.py` — `FridgeClient`: собирает запрос «чтение регистров» (функция 0x03,
  `START_REGISTER`, `REGISTER_COUNT`), отправляет по UDP через asyncio и разбирает ответ.
  Проверяет длину, CRC, код исключения Modbus и обрезанные пакеты — всё это выливается
  в понятную ошибку, а не `IndexError`.
- `registers_to_values()` — какие регистры что значат, задаётся индексами в `.env`
  (`TEMPERATURE_REGISTER_INDEX` и т.д.). **Это единственное место, которое надо
  «научить» новым регистрам.**

### `app/services/poller.py` — опрос
Одна `asyncio.Task` на камеру (аналог `QThread` из оригинала). На каждом цикле `poll_once()`:
1. читает значения;
2. успех → `failures = 0`, состояние online, проверка порогов по каждому активному
   параметру, запись в `measurements`, рассылка `measurement` по WS;
3. ошибка → `failures += 1`; после `OFFLINE_AFTER_FAILURES` подряд камера признаётся
   offline, в БД пишется строка `online=False` со значениями `NULL` (так разрывы
   видны на графике и в выгрузке). Единичный потерянный пакет ничего не меняет.

**Алерты — только на переходы.** Состояние хранится в `self.online` и `self.breaches`.
Первое состояние после запуска (`None → online/offline`) переходом не считается —
иначе каждый перезапуск сервера слал бы «камера отключилась» по всем мёртвым камерам.
Оно пишется только в журнал.

### `app/services/thresholds.py` — пороги
- Таблица `thresholds`: `(chamber_id, parameter)` уникальны, `parameter` — значение
  `ThresholdParameter` (`temperature`, `humidity`). Новый параметр = новое значение enum.
- При старте `load()` читает всё в память и создаёт значения по умолчанию для новых камер.
  Поллер проверяет по кэшу — БД не дёргается раз в секунду.
- `update()` — единственный путь изменения: валидация → запись → `audit_log` (старое и
  новое значение, имя, IP, имя компьютера, браузер, комментарий) → журнал → алерт
  `threshold_changed`. Изменения сериализуются `asyncio.Lock`.
- `evaluate()` — гистерезис: выйти за границу можно сразу, вернуться в норму — только
  отступив на `THRESHOLD_HYSTERESIS`. Без этого температура, дрожащая на 8.00/8.01,
  слала бы пару breach/recovery каждую секунду.

### `app/services/alerts.py` — пул уведомлений
- `publish()` неблокирующий: кладёт `AlertMessage` в очередь.
- Диспетчер: запись в `alert_events` → строка в `journal.log` → WS-рассылка всем вкладкам →
  попытка доставки во все каналы.
- Если каналов нет (`TELEGRAM_BOT_INTERNAL_URL` пуст) — событие сразу помечается
  доставленным, retry его не трогает.
- Retry-цикл берёт до 50 недоставленных, доставляет параллельно (не больше 5 одновременно).
  После `ALERT_MAX_ATTEMPTS` сдаётся и публикует локальное (без Telegram) событие
  `delivery_failed` — его видно в браузере и журнале.
- Новый канал (email, SMS) = класс с `name` и `async send(event)`, добавить в
  `configure_channels()`.

### `app/services/broadcaster.py` — WebSocket
Рассылка идёт по снимку списка соединений, параллельно, с таймаутом 5 с на клиента;
упавшие соединения выкидываются. `api/ws.py` убирает соединение в `finally` при любом обрыве.

### `app/api/`
- `export.py` — камеры, история, выгрузка, импорт.
  - История за период: если точек больше `MAX_CHART_POINTS` (4000) — `_BucketSampler`
    режет ряд на корзины и из каждой берёт точку минимума, максимума и первую точку без связи.
    Поэтому пик в одну секунду за месяц не пропадёт с графика.
  - Выгрузка — полная, без прореживания; время в `TIMEZONE`; CSV в `utf-8-sig`
    (Excel сразу видит кириллицу); временный файл удаляется после отправки.
    Excel-выгрузка больше 1 млн строк запрещена (лимит формата) — предлагается CSV.
  - Импорт — разбор на сервере через pandas, в БД не пишется. Колонки ищутся по точному
    совпадению нормализованного имени (`Temperature`, `Температура, °C`, `temp`, …;
    `Date`+`Time` или `datetime`/`recorded_at`). CSV с `;` и десятичной запятой тоже читается.
- `thresholds.py` — `GET/PUT /api/thresholds`. IP клиента — из соединения
  (или `X-Forwarded-For` при `TRUST_PROXY_HEADERS=true`), имя компьютера — обратный DNS
  с таймаутом 1.5 с. Имя пользователя Windows браузер не отдаёт в принципе, поэтому
  «кто» — необязательное поле формы (сайт запоминает его в браузере).
- `journal.py` — `/api/alerts`, `/api/audit-log` (+ `/export`), `/api/journal/download`,
  `/api/health`.

### `app/logging_setup.py` — журнал
- `logs/climatica.log` — общий лог приложения.
- `logs/journal.log` — журнал событий и действий: старт/стоп, начальное состояние камер,
  каждый алерт, каждая доставка/отказ, каждое изменение границ. Формат:
  `2026-09-28 00:05:43+0300 | THRESHOLD CHANGED chamber=1 ...`
- Ротация по 10 МБ, хранится 20 частей; `/api/journal/download` склеивает их по порядку.
- То же самое продублировано в БД (`alert_events`, `audit_log`) — оттуда берётся
  выборка за период.

### `app/models/db.py` — схема
| Таблица | Что хранит |
| --- | --- |
| `measurements` | Все измерения: температура, влажность, уставки (NULL, если не читаются), `online`, время (UTC) |
| `thresholds` | Границы по (камера, параметр), `enabled`, кто/когда менял последним |
| `alert_events` | Пул уведомлений и статус доставки (`delivered`, `delivery_attempts`, `last_error`) |
| `audit_log` | Действия пользователей: было/стало, имя, IP, компьютер, браузер, комментарий |

Миграций нет: `create_all` при старте + несколько `ALTER TABLE … IF NOT EXISTS` для
баз, созданных первой версией (где `temperature` был `NOT NULL`, а влажности не было).

## 3. Фронтенд (`app/static/index.html`)

Один файл без сборки. Все библиотеки лежат в `static/vendor/` — на площадке с
камерами может не быть интернета (именно из-за CDN когда-то отображалась только
первая камера: `Chart is not defined`).

- Порядок скриптов важен: `chart.umd.js` → `hammer.min.js` → `chartjs-plugin-zoom` →
  `chartjs-adapter-date-fns`.
- **chartjs-plugin-zoom требует все подключи `zoom.wheel/pinch/drag`** — частичный
  конфиг роняет создание графика с неочевидной ошибкой.
- Два своих мини-плагина Chart.js: `offlineBands` (красная заливка периодов без связи)
  и `thresholdLines` (пунктир границ). Ось Y подстраивается, чтобы пунктиры были видны.
- Режимы панели: `live` (точки идут по WS) и `history` (период из БД, WS-точки на график
  не добавляются, статус камеры обновляется). Импорт открывается отдельной панелью.
- Сообщения WS: `measurement` → панель; `alert` → всплывающее сообщение внутри страницы
  (работает всегда), системное уведомление (если вкладка скрыта и есть разрешение),
  обновление порогов и журнала.
- Системные уведомления браузера доступны только в secure context: `https://…` или
  `http://localhost`. По `http://192.168.x.x` браузер их запрещает — это не обходится
  кодом. Для этого нужен HTTPS (см. «Дальнейшие шаги» в README). Основной канал — Telegram.

## 4. Telegram-бот (`bot/`)

- `config.py` ищет `bot/.env` рядом с собой, независимо от рабочей папки.
- `AlertBot.handle_send` — `POST /internal/send`: проверка `X-Internal-Token`
  (если задан), форматирование (HTML-экранирование, время в `TIMEZONE`), отправка
  всем `TELEGRAM_CHAT_IDS`. Если никому отправить не удалось — `502`, backend повторит позже.
  Без токена — «сухой режим», `200` + предупреждение в логе.
- Polling (не webhook): бот сам ходит в Telegram, поэтому работает из закрытой сети
  без белого IP и HTTPS.
- Команды `/status`, `/thresholds`, `/help` отвечают только разрешённым чатам;
  `/start` отвечает всем и показывает `chat_id` — чтобы его было откуда взять.

## 5. Как добавить влажность и уставки

Когда станут известны регистры:
1. В `.env` прописать индексы: `HUMIDITY_REGISTER_INDEX`, `TARGET_TEMPERATURE_REGISTER_INDEX`,
   `TARGET_HUMIDITY_REGISTER_INDEX` (индекс внутри блока, который читается с `START_REGISTER`;
   если нужный регистр вне блока — увеличить `REGISTER_COUNT`).
2. Если масштаб не «×100» — поменять `REGISTER_SCALE` (или, если масштабы у параметров
   разные, завести отдельную настройку в `FridgeClient.registers_to_values`).
3. Перезапустить. Код менять не нужно: значения пойдут в БД и по WS, на панелях появятся
   влажность и уставки, на графике — вторая ось, в блоке границ — влажность, поллер начнёт
   проверять пороги влажности (`active_parameters()`), выгрузка получит новые колонки.

Новый параметр с порогами (например, давление): значение в `ThresholdParameter` +
подпись в `PARAMETER_LABELS` + колонка в `Measurement` + индекс в `registers_to_values`
+ строка в `PARAM_INFO`/`SERIES` на фронтенде.

### Известные ограничения (осознанно не сделано)
- **Нет аутентификации**: менять границы может любой, кто открыл сайт в сети. «Кто» —
  самоназвание + IP + имя компьютера по DNS.
- **Нет миграций** (Alembic). Схема меняется `create_all` + ручными `ALTER`.
- **Рост таблицы `measurements`**: ~86 400 строк в сутки на камеру при опросе раз в секунду,
  офлайн-камеры тоже пишут строки. Индекс `(chamber_id, recorded_at)` держит выборки быстрыми,
  но со временем стоит добавить очистку/архивацию.
- **Системные уведомления браузера по http в сети не работают** — нужен HTTPS.
- **Первое состояние после перезапуска** не вызывает алерт (только запись в журнал).
- **`host`-сеть Docker** ломает имена сервисов — см. комментарий в `docker-compose.yml`.

## 7. Тесты

`pytest` в корне (SQLite вместо PostgreSQL, камеры и Telegram подменены):

| Файл | Что проверяет |
| --- | --- |
| `tests/test_units.py` | Разбор `CHAMBERS`, сборка/разбор Modbus-пакетов и битые пакеты, индексы регистров, гистерезис, форматирование сообщений бота |
| `tests/test_poller.py` | Переходы online/offline и норма/вне нормы — ровно один алерт на переход; запись офлайн-строк |
| `tests/test_api.py` | Весь HTTP API на настоящем приложении: история и прореживание (пик и разрыв сохраняются), выгрузка ↔ импорт CSV/XLSX, валидация порогов, аудит, алерт через WebSocket, повторная доставка и отказ после N попыток, журналы и копия журнала |
| `tests/test_bot.py` | Приём алертов ботом: сухой режим, токен, пустой список получателей → 502, рассылка всем |

Ручная проверка без железа — `tools/fake_chamber.py` (см. README).
